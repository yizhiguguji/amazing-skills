# 功能QA：选择、边界与持续需求

日常拿需求文档（有时有Figma）写或改用例，固定用 `qa-test-design` 即可。只有请求涉及多个交付阶段或不知道该选哪项能力时用 `qa-workflow`。不用人工选择等价类、边界或状态迁移Skill；用例技能根据测试条件选择这些方法并给理由。

| 当前任务 | Skill | 主要产物 |
| --- | --- | --- |
| 写、补、审查用例；需求细化、推翻、范围撤回 | qa-test-design | 当前用例、需求追踪、维度决策、缺口、变更差异 |
| 按用例执行/复测 | qa-functional-execution | 本轮实际观察、环境、结果和证据 |
| 提Jira、改缺陷、写复测备注、流转 | jira-defect-delivery | 草稿或逐动作回读回执 |
| 汇总/更新测试报告 | qa-test-report | 同一结果快照复算、风险、未测项 |
| 指定功能安全专项、越权等风险审查 | qa-security-review | 范围章程、用例/探索目标、授权内证据与限定结论 |
| 上述多个阶段或选择不明 | qa-workflow | 只加载适用能力，保留交接与授权边界 |

QA不经过finesse-brief、Impeccable、UI UX Pro Max的产品/界面设计流程：测试需要验证既有需求，不能为了写用例重新定义产品或增加功能。Figma作为相关视觉与交互证据，按项目约定优先级使用；访问不到就记录缺取证，不能假装看过节点。

## 怎样既专业完整又不扩大覆盖

先把需求拆为验收点和测试条件，再看直接受影响路径。交互、成功、异常、边界、状态始终作为候选；切应用、切后台、锁屏、断网、弱网、温度也逐项考虑，但只有相关性、依据与可判定结果成立时生成正式用例。

判断每个候选：

1. 它是否改变本期行为的入口、状态、输入或结果？
2. 预期有需求、设计、确认基线或实际转述支持吗？
3. 前置和数据是否能准备，操作与观察是否真实可行？

相关但预期未知：待明确，或探索观察，不判通过。相关且可判定但设备/数据不具备：可设计，执行时阻塞。无关联或明确范围外：记录不纳入理由。用户要求排除相关风险：保留限制与残余风险，不能记成无风险。

例如异步保存可能受到提交中断网、延迟重复点击、编辑时切后台的影响；这些是保存功能的条件变化，不是新增功能。只改静态文字通常不引入全套网络、热性能和账号回归。发热无风险线索、采集方式和验收判据时不造温度阈值；任务明确要求时记待准备/待明确，不能直接写不适用。

方法选择：输入约束用等价/边界，组合业务规则用决策表，状态变化用状态迁移，用户操作用正反场景，多因素组合才用pairwise，未知风险用有限探索。无需每个简单需求都使用全部方法，不用固定数量衡量专业性。

## 持续需求

用例复审与文字修订按 [目标与执行复核](../skills/qa-test-design/references/case-review.md) 处理：按独立目标判断拆合，相同规则的数据变体可参数化，不按步骤数或预期数机械拆分。文字整理保留已确认范围，执行人应能准备前置、找到对象、获取比较基准并逐项观察。拆合保留 ID/观察项映射与历史，格式检查不能证明语义等价。

本地冻结契约按具体内容比较；已冻结用例即使只是文字变化也要增加修订，不改原快照，新修订不继承旧通过。既有系统区分文字版本与业务版本时沿用该系统，不强制迁移。

每个来源、验收点和用例都有稳定身份/修订。新增建立新ID；细化更新受影响修订；替代/推翻记录被替代规则；撤回标状态并保留原稿。未变内容不机械重写。代码、评论与图稿新旧冲突不能只按最后时间定权威。

计划快照不等于批准。执行绑定当时修订，记录追加，不改旧结果。新预期未执行就是未执行，旧通过不自动继承。同轮失败后重试通过仍保留首次失败；独立复测轮可显示最新通过并保留历史。

项目已经有管理系统时保持其权威源和schema。没有系统时便携`.qa/`提供配置、计划、冻结来源、结果、变更和报告；不依赖原作者服务。SQLite写入只有配置了明确schema/授权/备份事务的adapter才考虑。

Jira 本地稿的 expected 支持原字符串或多项字符串数组，observations 可记录独立补充观察。无附件省略正文证据区，在回执记录证据状态；真实/模拟来源不能隐去，是否额外披露执行者和具体颜色/编号格式由项目决定。升级不覆盖历史草稿或改变已有摘要。完整字段与兼容行为见 [Jira交接](../skills/jira-defect-delivery/references/jira.md)。

## 换电脑安装与调用

```bash
go run ./cmd/amazing-skills install --target /项目/.agents/skills --skills qa-workflow
/项目/.agents/skills/.amazing-skills/amazing-skills qa init --project /项目
```

QA工作流复制六个自包含技能，使用Go编译的独立运行工具。Windows使用对应.exe，其他工具按其支持的Skill目录放置；不支持自动发现时AI直接读取SKILL.md即可。脚本根据自身位置找模板，不读创作者HOME或私有地址。写入辅助工具采用串行单写，不是多人服务后端。

没有实际设备/浏览器可完成用例设计并标未执行；没有已配置的Jira连接器可交付草稿并标未提交。Skill不是工具连接器；不能凭可读文本承诺任意电脑能控制原生应用。结构、引用和哈希检查不能证明业务覆盖或真实执行。

日常只需自然语言，不用提供完整提示词：

- “帮我根据这份需求出测试用例。”
- “需求改了，按新版更新一下。”
- “帮我测一下保存功能。”
- “整理这个Bug。”
- “汇总这轮测试结果。”

AI从当前材料、项目基线和上下文调度技能；方法、维度、范围控制、编号、历史和证据规则由Skill承担。只在关键业务预期、测试对象或必要目标配置无法确定时询问。只有文档时“测一下”先产生方案/用例；实际执行需要可访问的系统和环境。

安装在工具支持的发现目录后可直接说上述话。未安装/工具不支持发现时，首次告诉AI：“读取 ~/code/amazing-skills/skills/skill-router/SKILL.md，之后按我的需求自动选择技能。”同一会话不需每次重复；跨会话持续生效需在该工具的项目指令中保存这个入口位置。仅把仓库存放在磁盘上不会让任意AI自动知道它。
