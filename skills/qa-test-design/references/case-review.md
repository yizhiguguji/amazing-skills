# 用例目标与执行复核

用于审查既有用例、拆合目标和修订表述。按用户要求和项目规则选择检查深度；不把设计复核当作真实执行。

## 先固定本次允许改变什么

- 文字修订：沿用当前范围与业务预期，检查表达是否等价；不重新展开环境、账号或异常矩阵
- 用例复审：逐条核对目标、依据、可执行性、重复和已确认覆盖；疑似遗漏先核对整份用例集与已登记缺口
- 需求变更：按有效来源重新分析受影响行为；无关用例保留

将已确认的本期变化、直接受影响的兼容边界、已上线背景和未知规则分开。背景可用于必要前置，不能自动形成新增验收目标；未知规则记缺口，不生成固定预期占位。

## 判断是否需要拆合

用一句话写出本条要回答的问题，再检查各观察是否都在证明它。

- 同一归属或隔离规则的修改、切换、返回，以及多个字段比对，可以共同证明一个目标
- 展示与持久化等可以分别判定、修复和复测的行为，通常分别成例
- 前一步失败遮蔽后续独立目标时，考虑拆分或独立准备；同一目标的后续步骤依赖前一步，不因此机械拆分
- 相同规则的多组输入可参数化，写清每组起点、数据、预期和独立执行方式；不同业务规则不能藏在参数组中

例如，核对价格、币种和税额共同证明“读取目标订单”。同时验证订单展示、支付授权和退款成功，则涉及不同目标。例子只解释方法，不替项目决定范围。

按“触发＋前置状态＋数据边界＋操作＋观察位置＋判定依据”查重；标题相似或部分步骤相同不足以合并。拆合时保留稳定身份和原观察映射，不以用例数量作为质量目标。

## 按执行顺序逐条通读

- **前置可准备：** 写清所需身份、入口、起始状态和可区分数据。每条能独立准备，不依赖“上一条通过”；共享场景准备不共享判定结果
- **动作可操作：** 指明操作对象、入口、输入、触发和观察时机。多入口检查写清离开、关闭或返回的必要顺序；不能用“确认已完成”替代应执行的触发动作
- **指代能定位：** 群组、订单、面板等对象名称在本条内可辨认。不用未定义代码、数量简称或“同上”代替内容；必要的数据名称在前置定义，重复关键对象以避免歧义
- **比较有基准：** 写清比较哪个对象、哪个时点、哪些字段；区分操作前记录、操作后记录与另一对象记录。基准必须可获取，不能要求回查未提供的定义、版本或规则
- **预期可观察：** 对应实际动作和观察位置，写可判定结果；“正常、正确、一致”不能单独充当判据。检验状态保留、清除或隔离时，准备能区分正确与错误结果的数据，避免相同默认值或后一次覆盖掩盖问题
- **步骤与预期对应：** 按项目约定建立对应关系。同号格式下逐项核对操作、时机和结果；不要用无关断言凑齐数量，也不要让后续步骤的预期挤在前一步

例如：“订单二金额与订单二切换前记录的金额一致”能定位对象与时点；“金额一致”不够。具体字段直接写出，既不省略判断所需内容，也不重复整段需求。

## 修改后核对

- 对照修改前后，核对目标、对象归属、触发时序、数据状态、观察位置和判定条件；把表述澄清与业务变化区分开
- 扫描同类用例是否存在同样问题；只修改受影响条目，保留未受影响正文、编号、归属、审批和历史结果
- 重新核对已确认目标与分支的覆盖，不能仅凭数量或格式宣称没有遗漏
- 按项目格式核对编号、换行、命名和导出；这些格式约定不提升为所有项目的强制要求
- 已授权同步时回读系统和约定交付文件的实际内容；仅生成草稿或同步失败时说明状态，不冒称已入库

结构校验、语义复核、人工评审和真实执行分别报告。有限样例验证只证明这些样例的表现，不能证明技能在所有需求上都不会出错。

## 与本地冻结契约接续

本地 schema1 冻结的是具体内容：已冻结条目的文字变化也需要保留原版并增加 revision，不能以“语义没变”为由改写冻结快照或绕过 Go 校验。文字修订不必扩大业务范围，但新修订不继承旧执行通过；是否需要复测及深度按项目规则决定，未执行就明确未执行。既有系统有独立的文字版本与业务版本时沿用其机制，不强制迁移成本地结构。

拆合在既有变更记录中登记“原 ID@revision → 保留/新增 ID@revision → 原观察项去向”，同时修订需求引用、追踪和维度关联；被撤回条目标 retired，保留冻结身份和历史结果。此映射是模型复核依据，Go 只验证结构、身份和修订，不证明拆合语义等价。步骤和预期按项目约定对应，不强制二者数组长度相等。
