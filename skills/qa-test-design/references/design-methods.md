# 由测试条件选择方法

先提取验收点和直接受影响行为，写“条件→风险→方法→场景→依据”。没有规则就标未知，不先列大量空泛用例再反向找需求。

| 条件 | 方法 | 必须得到的结果 |
| --- | --- | --- |
| 一条用户流程/交互 | 场景法 | 成功路径、合法替代、取消/返回及异常恢复；入口与观察位置明确 |
| 输入、集合、权限类别 | 等价类 | 有效、无效、未知分区和代表值；不能凭空定义合法格式 |
| 已知长度/数量/日期/时限边界 | 边界值 | 下界/上界及相邻值，标单位、包含关系和计数算法；未定义上限列缺口 |
| 多条件业务规则 | 决策表 | 条件、可行组合、动作与预期；无法发生的组合剔除并说明 |
| 状态/历史影响行为 | 状态迁移 | 状态、事件、合法/非法迁移及重要序列；切后台、锁屏是不同事件 |
| 多个独立参数造成组合爆炸 | pairwise/风险组合 | 因子和值、约束、覆盖目标与未覆盖高阶风险；不是穷举的代名词 |
| 需求稀疏但有高风险/未知 | 错误猜测/探索章程 | 明确同一行为的观察目标、时间/操作预算、环境、证据；未知预期不判通过 |

通常：简单交互用场景+少量状态；表单用场景+等价/边界；组合规则才用决策表；多因素才考虑pairwise。无需所有方法齐上。优先影响×发生可能性决定深度，不用固定用例数或武断覆盖百分比。

边界细节：字符串按字符、Unicode码点、字素或字节计数由来源明确；跨天按时区；小数按精度与舍入；空白与空字符串不能假定等价。性能要求必须有已确认阈值、单位、统计窗口与可获取证据；未知阈值只做观察比较。

状态细节：进入页面→修改→提交中→完成/失败→返回，明确每个触发观察哪个状态。前置不能破坏“第一次/无记忆/未授权”；恢复应直接看恢复页面，不以重开替代。

可参数化相同业务断言的输入/平台，但必须保留失败定位；有不同预期或独立恢复路径时拆用例。多步端到端不等于非原子，原子性指清晰测试目标。

追踪矩阵同时列已覆盖、可执行但未测、待明确、范围外；不能用“已有相似用例”填满。必要的探索发现经业务确认后再转正式用例，不把经验猜测直接变需求。
