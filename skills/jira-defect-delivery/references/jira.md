# Jira交接契约

输入draft JSON：id、summary、environment、steps数组、actual、expected、basis（可读出处）、evidence项目内相对文件数组。expected 兼容原非空字符串，也可用非空字符串数组表达多项预期；字符串保留已有换行/格式，数组多项生成有序列表。可选 observations 为非空字符串数组，表示不与主异常混淆的补充观察。evidence 必须显式提供，可为空数组；空数组时正文省略整个证据区，缺口保留在命令回执的 evidence_count/evidence_status 中。severity/priority/assignee只有明确映射与账户依据才填。问题ID使用本地稳定标识，不伪造外部单号。

## 正文表达与排版

- 环境、复现步骤、实际与预期应让执行人能定位对象、操作、观察时机及比较基准；不写未确认推测。异常先陈述，补充观察另列；多项独立预期分行。具体编号、加粗、颜色与模板服从用户及项目规则，颜色不能成为唯一标识，不强制强调色或统一格式。
- 保存必要的真实执行环境、来源及限制，模拟不伪装为真实执行。是否对外注明执行者或工具由用户、项目与实际判断需要决定；不自动添加整理过程，也不一律删除执行方式。来源/方式等追溯记录仍须保留。
- 只有实际证据才增加证据区；无附件不在正文生成空标题或“暂无证据”等占位。若缺证据影响异常是否成立，应保持待确认，不能因正文省略而隐去缺口。现有媒体保留顺序、比例与可访问性；日志或抓包按实际项目规则处理。
- Go 助手生成 Markdown 本地稿，不负责目标平台的富文本编码。连接器使用其支持的列表/富文本格式，不能把未解析的 Markdown、HTML 或 ADF 源码当成可见正文。平台不支持某样式时用清楚的分段或文字交付，不因样式差异阻塞内容。

提交后回读实际内容、排版及媒体，不只看接口成功。只改授权字段，保留原内容与有效媒体。新格式不会改写已存在草稿：若旧正文与新版不同但完全匹配相同输入的旧版生成结果，重跑保留旧正文及其 payload_hash，返回 legacy-preserved；如要升级正文另建明确修订，不能自动覆盖或改变既有回执摘要。

## 精简正文与设计对照

- 从接单人视角写清触发操作、实际差异和预期表现，分别定位业务文档与设计交互。引用评论前核实作者及结论状态，测试侧判读不能标成产品确认；平台系统界面与应用自有界面分别判断。
- 保留本轮真实版本、构建及适用的设备信息；项目需要安装包链接时记录完整可复制且可访问的链接，不强制所有问题提供安装包。不同时间或构建的观察分别标注，不拼成同一次复测。链接仍按目标平台的访问与保密要求处理。
- 有对应设计的视觉差异，按项目需要选择并排对照或分别引用同场景实测与设计原图，不强制合成同一张图。分别标明来源，例如“实测”“设计”，真机、浏览器或模拟画面如实标识。排版保持比例，不遮挡关键控件，不用生成式工具重绘原始证据；裁取局部时保留定位，原图、版本和来源仍可访问。逐张检查状态、文字和清晰度；无对应设计的业务或时序问题保留实际证据与文档依据，不拼无关图或把未定设计画成预期。
- 需要排版时使用目标环境已有且可用的工具，不因整理缺陷自动安装依赖。缺工具时保留原图及一一对应的来源，按实际交付范围说明未完成项；生成对照文件不等于已上传、正文可见或远程回读成功。
- 当前正文聚焦当前问题。历史原描述、原图和旧判断保留在平台可访问的历史记录或明确链接的归档附件中，不能仅留本地备份，也不反复嵌套整段旧正文。整理不删除旧附件、评论或有效证据，不改变问题状态或测试结论；历史不可访问时先保留原正文并说明归档缺口。
- 用户已整理且要求保持不变、或明确排除的单及字段建立保护清单。写前核对最新编辑，写后核对当前正文、原附件与评论、实际需要的对照图及受保护字段；只改本次授权部分。

## 需求变更与撤回

在既有QA或缺陷变更任务中读取新版需求或设计时，检查原范围内开放问题是否仍成立，同时检查受影响用例与已有实测证据。明确规则直接用于影响判断，不把已经清楚的结论重复交产品决定。纯资料阅读或摘要请求不自动扩展为资产修改；外部同步按实际授权执行，新异常先查重，无实际异常证据只列待验证候选。

- **整单撤回**：保留原问题、原预期、实际证据及原设计图。标题保留问题含义，按项目规则可增加完整撤回标识；用户要求恢复原标识时查标题历史，不自行缩写或猜测。使用目标项目实际可用的撤回、忽略或其他映射，不硬编码状态名，不把撤回记为修复通过，也不从现有状态反推原因。
- **变更后仍需修复**：只更新仍属同一Bug的受影响预期、依据和设计对比，保留原始步骤、实际现象、实测证据及历史评论。旧设计图标明变更前版本并保留，新增当前图和定位，不静默替换。未按新要求复测，不沿用旧结果判断新修订通过或失败；独立问题查重后另行处理。
- **部分撤回或尚待决定**：按原条目编号列明撤回、继续修复和待决定项，仍有有效问题时不使用整单撤回标识或关闭整单。只将来源无法确定的具体问题交适当责任人决定；多项清楚编号，只提及目标项目中确需处理且已核实的人员。
- **评论只写增量**：补新增变化、处理决定、复测结论或待决定问题，不照贴正文已有的环境、步骤、完整预期、依据和媒体。新增来源、依据版本变化或原依据不足以解释决定时，补最短必要出处；已有有效评论已说明同一变化时不重复追加，有新决定再补并保留旧评论。
- **保留有助于判断的信息**：不往缺陷评论里堆叠“已更新描述”“已保留截图”等操作回执，不机械催办、重复可见标题状态或提及无关人员。未测范围和执行限制在直接影响本单结论时保留，不能因精简隐藏证据缺口或模拟来源。面向用户的交付仍报告实际修改、失败和未完成项。

示例仅说明表达，不定义产品规则：整单撤回可写“该交互要求已取消，本单撤回，无需修复”；部分撤回可写“1. 已取消的交互项撤回。2. 仍不符合当前要求的入口继续修复”。实际措辞须有当前来源支持，不能套用示例替代判断。

修改前核对最新来源、原值和已有编辑；修改后分别回读标题、正文、状态、评论和媒体。上述处理不扩大外部写入授权，等级、字段、负责人、关闭方式与保留期限由目标项目决定。

## 写入与回执

外部操作选当前AI已授权的连接器/CLI/API。配置来自用户项目，凭证不进入Skill、正文、日志或导出。没有连接器仍可查本地重复和交付稿，不能借机自动安装陌生插件。JiraCloud/Server等API与富文本格式由adapter决定，不能统一假设wiki或ADF。

回执JSON：mode（mock/live）、operation_id、operation（create/update/comment/transition）、issue_url、write_outcome（saved/unknown/failed）、readback_confirmed、expected_payload_hash、readback_payload_hash、evidence_entries（含local、uploaded、visible、remote_id）、relationship_saved（可选，仅项目需要时）、final_state（可选，流转必须有）。hash应取规范化payload；是否真正回读必须以实际连接器返回为证，布尔字段不证明网络。

只有saved、回读已确认、hash相等、需要的媒体上传且可见、必要关联保存后，当前动作才完整。unknown/failed时返回待恢复/失败，不盲目重建；真实已创建单可存在于部分成功状态。通过检查返回的是动作回执状态，不把mock变live，不替代人工复现。

复测comment、字段update、transition分别生成回执；状态变更不能代替必要的处置说明，但已有清楚有效的评论时不重复发送。目标状态缺规则就保留不变；负责人来自当前用户或真实责任配置，不复制相邻issue的人。
