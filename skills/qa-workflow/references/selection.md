# 如何选择和确定QA技能

先分辨交付动作，再选最小足够的技能。用户明确指定优先，持续需求查当前版本和已冻结快照，不以“最后修改的文件”自动决定权威来源。

功能测试默认黑盒，不要求代码、Appium、Xcode或测试桩。能使用实际授权工具时取证；设备、账号或工具不存在就准备可审阅内容并说明未执行。

简单需求也应考虑交互、成功、异常、边界和状态变化；后台、切应用、锁屏、断网、弱网、温度是相关行为的条件维度，不是必须全量生成的功能清单。完整性来自“每个相关验收点有测试条件、每个候选维度有理由”，不来自用例数量。

将覆盖分为三类：

1. 本期要求及直接受影响路径：正式用例，引用当前需求或已确认基线。
2. 同一行为的环境/状态变化：相关且有判定依据时纳入；预期未知先澄清或用探索章程记录观察。
3. 相邻业务、全产品专项、未授权平台或未知性能目标：明确范围外或建议后续，不能悄悄加入本期。

例：只改保存按钮文案，核对对应状态下的文字、布局及可操作性，不重测全部账号系统；修改异步保存，则保存前/中/后切后台、网络中断与重复点击可能直接影响结果，相关风险应进入候选。明确排除相关风险时保留原因和残余风险，不把“未测”改成“无需测试”。

交付顺序可以是设计→执行→缺陷→报告；需求变更回到设计，复测回到执行；报告不反向改变来源、用例审批或结果。每次转交带稳定ID、修订、来源版本、授权及可观察完成条件。

## 自然语言调度与默认行为

以下是语义示例，不是关键词匹配器；结合对象、上下文和现有产物判断，不要求用户照抄。

| 用户的说法 | 默认推进 |
| --- | --- |
| “帮我出用例”“看看这个怎么测”＋需求或设计稿 | 调用用例设计，自动选方法、相关维度和项目格式；交付初版与必要缺口 |
| “帮我测一下这个需求” | 有可访问的目标、环境及可执行范围时设计并执行相关检查；只有文档时先完成测试方案/用例并明确未执行，不伪造测试结果 |
| “需求改了”“这条不要了”“按新版更新” | 定位当前基线与新来源，分析新增/细化/撤回，只修订受影响用例并标重测；存在多个无法区分的版本时询问来源 |
| 既有QA任务中“阅读新版需求／设计”“文档更新了” | 联查原范围用例增补／修订／撤回、开放缺陷是否失效，以及已有实测证据中的新异常／漏提；形成影响及同步清单，明确规则不重复询问。纯阅读、摘要或比较请求止于分析；保存资产、执行与外部写入按实际授权分别推进，无实际观察的候选不称已发现Bug |
| “这个安全上有没有问题”＋当前功能 | 安全专项做来源审查与范围内方案；执行需实际目标/环境/动作授权，目标不明只澄清对象 |
| “登录这块重点测越权”“给上传功能做安全用例” | 安全专项，只限指定行为；用例请求止于设计，不自动扫描/改请求/建单 |
| “帮我出用例，顺便看看安全” | 功能用例设计结合相关安全筛选，复用已有负向/边界用例；上下文未要求专项时不增加全产品专项 |
| “继续”“再补全一点” | 接续最近的QA产物和已确认范围，补漏或完成未完成步骤，不重启流程或自动扩大到全产品专项 |
| “这里有问题”“帮我整理这个Bug” | 根据实际观察形成缺陷草稿；缺复现/预期依据的部分列缺口；不自动提交Jira |
| “提交这个Bug到Jira” | 交接缺陷技能，使用已配置项目与实际连接器；明确提交指令已是授权，缺关键目标配置时再问 |
| “汇总一下”“给我测试结论” | 有执行记录时调用报告；只有用例时提供覆盖/准备情况，不能把计划写成测试通过 |

仅文案/样式变更不自动回归完整身份系统；不存在角色/接口时不假设它们存在。“安全”“全面”“补全”不是覆盖所有资产的授权。已有测试目标承接上下文，除依赖执行的关键事实外不要求长提示词。

每次自动继承：功能黑盒、需求约束范围、相关维度决策、专业设计方法、编号与变更历史、事实与假设分离、真实证据要求。项目已确认规则优先；用户明确的新要求覆盖原有默认。未知业务预期保持待明确，不能以“自动补齐”名义编造。

缺少输出格式、用例数量、方法名称或非关键偏好时采用项目惯例/便携默认，不阻断。确实没有需求对象时只问“需要测试哪个功能？提供需求描述或文档位置即可”；多个关键问题合并一次询问，同时继续可独立完成的部分。不要求用户填写所有配置，也不重复确认已授权动作。
