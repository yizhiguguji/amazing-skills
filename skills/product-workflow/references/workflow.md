# 阶段与选择

| 当前情况 | 下一步 | 输出 |
|---|---|---|
| 模糊工作台，无规格 | workbench-definition | 完整草案、假设、验收 |
| 规格可实现，视觉抽象或有参考待提取 | design-reference-extraction → interface-delivery | 有证据的设计包、组件预览及固定 DESIGN.md |
| 规格与设计已有 | interface-delivery 实现阶段 | 代码及实际状态 |
| 可运行实现 | workbench-verification | 行为、视觉与规格证据 |
| 检查失败 | 回到有关阶段 | 修复后重验失败项与受影响项 |
| 局部修改 | 保留规范，直接实现检查 | 变更与对应证据 |

第三方选择：finesse-brief 仅用于工作台定义；Impeccable 优先处理设计、实现指导与精修；UI UX Pro Max 按需查图表、配色、字体、技术栈。已有 DESIGN.md 时不重新生成全局风格。允许用户明确改选外部技能。

缺口问题应集中问，只问会改变核心任务、数据可行性或实现范围的事实。可以同时提出可撤销草案，但不能把假设标成已确认。可在用户回答前完成不依赖回答的工作。内部路由和技能选择不是用户需要逐步批准的事项。

完整本地构建请求可一路执行，不人为增加阶段批准。用户只要求方案或外部技能明确需要尚未提供的关键信息时，完成已有工作并停在必要边界。发布、外部提交和消息发送根据实际授权单独判断，不能从本地构建推导授权。

完整需求第一版不承诺通用市场研究或生产后端。实现采用实际用户授权和项目约束；原型可用本地存储，但在规格中说明设备范围、同步和数据限制。

首轮完成后锁定 DESIGN.md 与实际 tokens，第二轮修改开始和结束都运行 check-design；不调用 Pro Max 全局设计系统生成。缺失引擎时可先显式 setup-engine，成功校验才执行。原型验证使用合成回答时，在输入和输出里标明，不能把它写成真实客户确认。

参考提取允许只有抽象描述，先交付可撤销方向与推断依据；不以缺少参考图或 CSS 参数阻断。组件预览是验证设计规范的中间产物，不能用它替代规格定义或实际产品验收。包由设计能力携带，不是另一个技能发现层；说明、命令及样例随单点能力或工作台依赖闭包一起安装。
